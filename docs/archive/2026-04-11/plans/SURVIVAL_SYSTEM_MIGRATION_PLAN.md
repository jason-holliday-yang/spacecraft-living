# SpaceCraft Living 生存系统迁移执行单（2026-04-07）

> 当前状态说明：本文件保留为迁移阶段历史执行参考。新版生存系统主结构已落地，当前不再按本文档继续扩展新状态范围，而以平衡、兼容清理和维护收尾为主。

## 1. 文档目的

本文档把新版 `血量 + 氧气 + 状态栏` 设计，拆成可直接执行的开发任务。

它和其他活动文档的关系如下：

- [`GAME_DESIGN.md`](/Users/jason/Documents/SpaceCraftLivng/docs/design/GAME_DESIGN.md)
  负责说明目标设计是什么
- [`STATUS_SYSTEM_MAPPING.md`](/Users/jason/Documents/SpaceCraftLivng/docs/design/STATUS_SYSTEM_MAPPING.md)
  负责说明区域、怪物、道具、装备、设施如何映射到状态系统
- 本文档
  负责说明工程上应该按什么顺序落地

本文档的目标不是讨论方向，而是降低真正开始改代码时的组织成本。

## 2. 迁移总原则

这轮迁移必须遵守以下原则：

1. 不同时改“系统结构”和“大量数值平衡”
2. 先让新系统能跑，再追求体验更好
3. 先替换主资源模型，再替换 UI 表达
4. 先让两个核心状态成立，再扩展更多状态
5. 每一轮改动都要保住主线可通和存档可读

## 3. 推荐实施顺序

建议固定按下面顺序推进：

1. 运行时数据结构迁移
2. 主资源结算迁移
3. HUD 基础布局迁移
4. 状态系统最小落地
5. 恢复点与道具职责迁移
6. 区域风险和怪物状态接入
7. 存档迁移与测试补齐
8. 最后再调平衡

原因：

- 如果先改平衡，后面结构变化会把调参推翻
- 如果先改 HUD，后面运行时字段一变，UI 还要重接一遍
- 如果先做一堆状态，没有统一主资源模型，状态职责会再次混乱

## 4. 分阶段任务

### Phase 0：文档与命名冻结

目标：

- 先把名词统一，避免后面边写代码边改术语

必须冻结的术语：

- `Health`
- `Oxygen`
- `Status Bar`
- `Poisoned`
- `Oxygen Leak`
- `Low Oxygen`
- `Suffocating`
- `Critical Condition`
- `Filtered`
- `Oxygen Reserve`
- `Camp Recovery`

完成标准：

- 活动文档中不再摇摆使用旧术语作为目标设计
- 代码里允许保留旧字段，但新实现必须围绕新命名组织

### Phase 1：玩家运行时模型迁移

目标：

- 把 `Player` 的运行时逻辑从旧资源结构迁移到新资源结构

建议改动范围：

- `include/player.h`
- `src/player.c`
- 与 `Player` 直接耦合的最小调用点

建议任务：

1. 新增或替换主资源字段：
   - `health`
   - `maxHealthBonus` 或等效字段
   - `oxygen`
2. 明确旧字段处置策略：
   - `stamina`
   - `pressure`
   - `poison`
3. 新增状态运行时容器：
   - 是否激活
   - 等级
   - 持续时间或强度
4. 保留现有背包、装备、资源数组不动

实现建议：

- 不要在第一步就彻底删除旧字段
- 允许先做“新字段生效，旧字段逐步失活”的过渡期

完成标准：

- `Player` 运行时可以独立表达 `血量 + 氧气 + 状态`
- 不再需要依赖旧版 `压力` 才能表达危险

### Phase 2：主资源结算迁移

目标：

- 把逐帧生存结算从旧版 `体力 / 压力 / 中毒` 模型改成新版 `血量 / 氧气 / 状态`

建议改动范围：

- `src/task_update.c`
- `src/player.c`
- 少量依赖阈值判断的调用点

建议任务：

1. 移除普通移动直接消耗“生命式资源”的旧逻辑
2. 改为区域耗氧主导外出风险
3. 改为低氧触发状态，而不是旧版低氧压低体力上限
4. 改为氧气过低或归零时触发 `窒息` 并持续掉血
5. 改为中毒通过状态系统持续影响血量与耗氧

阶段目标：

- 先让新版规则跑通
- 先不追求完美数值

完成标准：

- 玩家死亡主要来自 `血量归零`
- 玩家撤退压力主要来自 `氧气不足`
- 危险解释主要来自 `状态栏`

### Phase 3：状态系统最小落地

目标：

- 先做一套最小但完整的状态系统

首批必须实现的状态：

- `Poisoned`
- `Oxygen Leak`
- `Low Oxygen`
- `Suffocating`
- `Filtered`
- `Camp Recovery`

建议改动范围：

- `include/player.h`
- `src/player.c`
- `src/task_update.c`
- 新增或调整少量状态辅助函数

建议任务：

1. 定义状态枚举
2. 定义状态实例结构
3. 实现状态添加、升级、降级、清除逻辑
4. 实现状态优先级排序逻辑
5. 实现 Tooltip 文本查询入口或内容表对接

完成标准：

- 状态不是零散的 bool，而是统一系统
- 同类状态可以升级，不会重复堆叠一排图标
- 状态逻辑能被 HUD 和存档复用

### Phase 4：左下角 HUD 改版

目标：

- 把左下角 HUD 正式改成 `状态栏 -> 血量条 -> 氧气条`

建议改动范围：

- `src/ui_status.cpp`
- 必要时补充 `src/ui_layout.cpp`
- Tooltip 命中与状态描述入口

建议任务：

1. 加入状态栏布局
2. 重做下方两条资源条
3. 状态图标先允许使用占位图或程序化占位
4. 鼠标悬浮时显示状态说明
5. 保留当前整体 UI 语言，不要一次改太多窗口样式

完成标准：

- 玩家能在左下角一眼看到三层信息
- 没有图标资源时，状态栏也能工作

### Phase 5：恢复点与道具职责迁移

目标：

- 让基地、营地、食物、药用资源、防护服在新系统中职责清晰

建议改动范围：

- `src/task_actions.cpp`
- `src/player.c`
- `src/recipe_catalog.cpp`
- 相关提示文本内容

建议任务：

1. 基地恢复：
   - 完整回血
   - 完整补氧
   - 清除异常状态
2. Field Camp 恢复：
   - 部分回血
   - 部分补氧
   - 获得 `Camp Recovery`
   - 有限缓解异常
3. 食物重映射：
   - 主要回血
4. 药用资源重映射：
   - 解毒
   - 降低异常恶化
   - 临时过滤
5. Protection Suit 重映射：
   - 提供 `Filtered`
   - 降低危险区耗氧
   - 降低中毒和漏氧风险

完成标准：

- 玩家能明确感知基地和营地不是一回事
- 道具用途不再和旧版“减压力”绑定

### Phase 6：区域与怪物接入状态系统

目标：

- 让区域风险和怪物风险真正接入新状态系统

建议改动范围：

- `src/map.c`
- `src/task_update.c`
- `src/task_content.cpp`

建议任务：

1. 森林接入低耗氧规则
2. 外沼泽接入中耗氧规则
3. 深沼泽接入高耗氧 + 中毒核心规则
4. 遗迹接入高耗氧 + 漏氧 / 终局危险规则
5. 怪物攻击按类别接入：
   - 纯掉血
   - 中毒
   - 漏氧
   - Boss 复合风险

完成标准：

- 每个区域的威胁结构不只是“数值更高”
- 每类怪物有更明确的危险身份

### Phase 7：存档迁移与兼容处理

目标：

- 让新系统能安全保存和读取

建议改动范围：

- `include/save_system.h`
- `src/save_system.cpp`
- `src/save_legacy_adapter.cpp`
- `src/game_session.cpp`

建议任务：

1. 为新主资源补充存档字段
2. 为状态系统补充存档字段
3. 明确旧存档读入时如何映射：
   - 旧 stamina -> 新 health/默认恢复策略
   - 旧 pressure -> 丢弃或转为默认状态
   - 旧 poison -> 转为 `Poisoned` 状态等级
4. 保证旧存档至少能安全加载，不会崩

完成标准：

- 新存档完整保存血量、氧气和状态
- 旧存档加载后仍能进入可玩状态

### Phase 8：测试补齐

目标：

- 给新系统建立最小回归保护

建议新增测试主题：

1. `health_oxygen_smoke`
   - 血量与氧气基础阈值
2. `status_system_smoke`
   - 状态排序、升级、清除
3. `camp_recovery_smoke`
   - 基地与营地恢复差异
4. `save_status_smoke`
   - 状态存档与读档
5. `endgame_new_survival_smoke`
   - 新系统下终局三路线基础可跑

完成标准：

- 新系统核心路径有最小自动化保护

### Phase 9：平衡与体验打磨

目标：

- 在结构稳定后再调体验

当前执行结果（2026-04-08）：

- 已进入数值打磨阶段，不再改动主资源结构与存档结构
- 已开始围绕区域耗氧梯度、深沼泽二元压力、Boss 瞬时尖峰、和平路线准备收益做小步调参
- Phase 9 的目标是让“准备充分时明显更稳”，而不是把高风险区改成低风险区

重点关注：

- 前期是否仍然过松
- 深沼泽是否仍然过于二元
- Boss 是否从“会机制就秒”变成“会机制明显更稳”
- 和平路线是否真正体现氧气与装置准备价值

完成标准：

- 平衡调整不再和结构迁移缠在一起

## 5. 依赖关系

为了避免返工，建议遵守以下依赖顺序：

- Phase 1 完成前，不建议正式开做 HUD
- Phase 2 完成前，不建议正式调数值
- Phase 3 完成前，不建议扩充状态种类
- Phase 5 完成前，不建议大改区域平衡
- Phase 7 完成前，不建议宣布新系统可长期存档使用

## 6. 每轮开发的验收模板

每完成一个阶段，至少要确认：

1. 主线是否仍可推进
2. 左下角 HUD 是否仍清晰可读
3. 存档是否仍能安全加载
4. 死亡恢复规则是否仍成立
5. 当前改动是否已经同步进活动文档

## 7. 推荐第一轮实际开工顺序

如果现在立刻开始写代码，我建议第一轮只做下面这些：

1. 给 `Player` 增加 `health` 与状态容器
2. 让旧 `stamina` 暂时不再承担“主生命值”语义
3. 在 `task_update` 里先跑通新版氧气阈值逻辑
4. 落地 `Low Oxygen` 与 `Suffocating`
5. 在 HUD 左下角加状态栏占位

原因：

- 这是最小闭环
- 做完就能开始看到新系统的骨架
- 风险比直接同时重做中毒、营地、装备、Boss 要低很多

## 8. 本文档的使用方式

这份执行单适合在真正开始改代码前快速对照。

正确用法是：

- 做一轮前，先选一个 phase
- 做完后，对照该 phase 的“完成标准”验收
- 如果需要加新任务，优先补在对应 phase 下，不要另起一套顺序
