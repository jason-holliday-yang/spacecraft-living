# SpaceCraft Living 未来能力预留说明

## 1. 文档目的

本文档只回答一个问题：

- `在当前最终玩法范围已经冻结后，项目还保留哪些极小的未来接口位`

当前答案非常克制：

- `只保留少量账号能力预留`

它不是当前开发计划，也不是功能承诺。

## 2. 当前明确不做的事

当前项目范围已经冻结为单机本地生存探索游戏，因此下面这些不在当前开发范围内：

- 新地图扩展
- 新剧情主线
- 新大型玩法系统
- 在线大厅、多人协作、排行榜或社交系统
- 依赖远程服务才能游玩的账号体系

## 3. 当前唯一明确保留的未来接口位

如果未来真的要补充额外工程能力，当前只建议保留下面这一类能力：

- `注册 / 登录 / 账号绑定`

保留它的原因不是因为现在就要做，而是因为这类能力将来可能用于：

- 账号身份识别
- 云端存档绑定
- 多设备设置同步
- 成就或个人进度展示

## 4. 接入边界

如果未来真的要做注册 / 登录，必须遵守以下边界：

1. `本地单机闭环优先`
   游戏必须仍然支持本地离线启动、游玩和存档，不得把账号登录变成进入游戏的前置条件。

2. `账号层不能阻塞主循环`
   登录失败、网络异常或服务不可用时，玩家仍应能进入本地单机流程。

3. `账号层不能重写当前本地存档主路径`
   现有本地存档仍应继续存在。未来若要做云端能力，也应是在本地存档之上增加同步层，而不是直接替换。

4. `模块必须独立`
   账号相关逻辑应作为独立模块接入，不得把网络、鉴权或账户状态直接塞进现有 gameplay、task、UI 或 save 的大协调文件。

## 5. 推荐的技术落点

如果未来进入实现阶段，建议按下面的最小边界落地：

- 新增独立 `auth` 或 `account` 模块
- 主菜单只增加一个可选入口，例如 `Account`
- 账号状态只影响可选服务能力，不影响本地游戏主流程
- 云同步如要接入，应放在持久化层上方，而不是侵入玩法运行时

## 6. UI 预留建议

为了避免未来改动过大，可以只在心智模型上保留下面的 UI 预留位：

- 主菜单可选增加 `Account`
- 设置页可选增加 `Profile / Sync`
- 存档页未来可选显示 `Local / Cloud` 状态

当前不需要提前把这些 UI 做出来，只需要避免把菜单结构写死到完全无法追加可选入口。

## 7. 当前结论

当前项目的主要目标仍然是：

- 平衡现有游戏
- 修复现有问题
- 完成现有设计

注册 / 登录只是未来可能存在的工程预留位，不是当前执行任务。
